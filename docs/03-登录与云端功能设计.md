## 1. 关键技术决策

### D1 登录方案：Web 二维码扫码

TV 无 IME（P7 backlog 已确认中文输入是独立难题），账号密码 / 短信均不可行。
采用 Web 端扫码登录：TV 屏出二维码 → 用户哔哩哔哩 App 扫码确认 → 轮询拿 Cookie。
（B 站 TV 专属 appkey 方案需要官方签名与审核，不适用第三方，明确排除。）

### D2 Cookie 传递：JS 层全权管理（本设计核心）

源码级结论（Capacitor 7，node_modules/@capacitor/android）：

- `plugin/util/HttpRequestHandler.java` / `CapacitorHttpUrlConnection.java` **零 Cookie 引用**——
  原生请求既不注入 WebView CookieManager 的 cookie，也不把响应 Set-Cookie 写回 jar。
- `plugin/util/HttpRequestHandler.java#buildResponseHeaders`：响应头按
  `TextUtils.join(", ", values)` 合并后**原样透传给 JS**（含 set-cookie，多条合并为一条）。
- 手工 `Cookie` 请求头可原生生效（P6.5 实测：ranking 借 buvid3 头通过 -352 风控）。

由此定案：

```
poll 响应 headers['set-cookie']            （原生透传，多条逗号合并）
  → JS 正则拆分（规避 Expires 内逗号）解析 SESSDATA / bili_jct / DedeUserID 等
  → localStorage('bilitv.auth.cookies') 持久化
  → http.js 手工 Cookie 头合并输出（buvid3 既有机制复用）
```

不依赖 WebView cookie jar（原生根本不读它）；`credentials: 'omit'` 保持不变。

### D3 扫码轮询状态机

| code | 含义 | UI |
|---|---|---|
| 86101 | 待扫码 | 二维码 + 「打开哔哩哔哩 App 扫一扫」 |
| 86090 | 已扫码待确认 | 二维码压暗 + 「已扫码，请在手机上确认」 |
| 86038 | 二维码过期 | 遮罩 + 「OK 刷新」按钮 |
| 0 | 登录成功 | 解析 Cookie → setLoginCookies → auth.refresh() → 关闭弹窗 |

2s 间隔轮询；generate 的 `url` 字段即二维码内容（`qrcode` 库 canvas 渲染，离线生成）。

### D4 1080P：playurl qn 升级

登录后 `qn: 64 → 80`（platform=html5 + high_quality=1 不变，仍是 MP4 durl 直链）。
响应 `quality` 字段回传实际清晰度，播放页信息行展示「清晰度 1080P」。
qn 映射：16=360P / 32=480P / 64=720P / 74=720P60 / 80=1080P / 112=1080P+ / 116=1080P60。
DASH（VIP 4K/HDR）是独立任务，不混入本批。

### D5 云收藏

- 夹列表：`GET /x/v3/fav/folder/created/list-all?up_mid={mid}&type=2`（首个 = 默认收藏夹）
- 夹内容：`GET /x/v3/fav/resource/list?media_id&pn&ps=20&order=mtime&type=0&tid=0&platform=web`
- 查态：`GET /x/web-interface/archive/has/fav?aid=` → `favoured`
- 收藏/取消：`POST /x/v3/fav/resource/deal`（rid=aid, type=2, add/del_media_ids, csrf=bili_jct）
- 默认夹 id 惰性获取并缓存；未登录时收藏按钮回退本地 stores/app.toggleFav，行为与 v1 一致。

### D6 云历史

- 列表：`GET /x/web-interface/history/cursor?ps=20&type=archive&business=[&cursor=JSON]`
  （cursor 增量翻页：{view_at, max, business}）
- 上报：`POST /x/web-interface/history/report`（aid, cid, progress, type=3, csrf）——
  播放中沿用既有 5s 节奏随本地 saveProgress 一并上报，静默失败不提示。
- 本地历史（stores/app.histAdd）继续保留：离线兜底 + 续播优先用本地（值相同）。

### D7 登录态与退出

- `stores/auth.js`：nav（`GET /x/web-interface/nav`，匿名 code 0 + isLogin）拉取登录态，
  {mid, uname, face, level} 缓存 localStorage('bilitv.auth.user') 实现秒开。
- 退出：`POST passport /x/passport-login/web/exit?csrf=`（best-effort）→ 清本地 Cookie 存储 → reset。
- 应用的「不存储任何账号凭据」文案修正为「凭据仅保存在本机」。

### D8 POST 通道

http.js 新增 `apiPost(path, params)`：`application/x-www-form-urlencoded`，
复用限频 / 超时 / ApiError 翻译；写接口一律带 csrf=bili_jct。

## 6. P7 实测修订（2026-09-27 模拟器验证）

### D4 修订：1080P 在 durl 通道不可达
- 实测：登录 + qn=80 + platform=html5，playurl 仍返回 quality=64（720P）
- **定论：`platform=html5` 的 MP4 durl 流为服务端硬上限 720P**，与登录态无关
- 1080P 唯一路线：`fnval=16` DASH + MSE 拼接（WebView MediaSource），列入 P8
- qn=80 参数保留（DASH 方案复用）；清晰度角标如实显示服务端返回值

### D2 修订：凭据主来源改为 crossDomain URL
- 实测：ATV UA 下登录成功响应仅下发一条 Set-Cookie（SESSDATA），bili_jct/DedeUserID/sid 全缺
  → 写接口（fav deal / exit）-111 CSRF 失败
- **修复：poll 成功时 `data.url`（crossDomain 跳转 URL）的查询参数携带全部 5 项凭据**
  `parseLoginUrl()` 解析（值保持原始编码，不做 decode），与 Set-Cookie 解析合并、URL 覆盖优先
- 影响登录闭环：修复后**必须重新扫码**（旧凭据无法补全 bili_jct）

### 端点修订
- `/x/web-interface/archive/has/fav` **已下线**（实测 404 HTML，含 v2 等变体）
  → 收藏态查询替代方案待定（候选：默认收藏夹列表比对 / deal 空参探测需 csrf）
- `/x/relation/followings` 可用，但**必须携带 buvid3/buvid4 指纹**（缺 → -352；无凭据 → -101）

### 其他实测结论
- 弹幕 XML（comment.bilibili.com/{cid}.xml）为 raw deflate；**生产端 fetch shim 会把二进制按文本解码致损坏**
  → 原生端必须走 `CapacitorHttp responseType:'arraybuffer'`（base64 透传），三级解压自适应保留
- 扫码弹窗关闭路径：popLayer onClose 回调不可用「轮询停止标志」做幂等 guard
  （成功路径先置标志再弹栈，会短路 emit('close')），需独立关闭标志
- **弹幕 XML 三重陷阱（本次排查 2 小时的核心结论）**：
  1. 生产端 fetch shim 把 deflate 二进制按文本解码（bytes 损坏）→ 原生必须 CapacitorHttp
     `responseType:'arraybuffer'`（base64 → atob → Uint8Array）
  2. pako `inflate(bytes, {to:'string'})` 的「string」是逐字节 charCode 映射而非 UTF-8 组合
     （中文弹幕全乱码、且字符串长度==字节数是特征信号）→ pako 只出 Uint8Array，
     解码统一 `new TextDecoder('utf-8').decode()`
  3. 弹幕文本混入控制字符时 `DOMParser.parseFromString` 不抛错而是返回 parsererror 文档
     （querySelectorAll('d') 得 0 条，静默失败）→ 用正则 `<d\s+p="([^"]+)"[^>]*>([\s\S]*?)</d>`
     提取 + XML 实体反转义
- 诊断技巧：window.__dmDebug 数组探针（拉取字节数/解压长度/内容头/解析条数），CDP 读取，
  比盲猜快一个数量级

## 10. P8 播放内核升级：DASH+MSE / 清晰度切换 / 心跳（设计先行）

### D18 DASH+MSE 1080P（探针实测 2026-09-28，scripts/probe-dash*.mjs）

**探针结论（匿名态 /x/player/wbi/playurl fnval=16，wbi 签名）**：
1. DASH 结构完整下发：`dash.video[]` / `dash.audio[]`（音视频分离 fMP4）
2. **匿名 DASH 仅给 480P/360P**（`quality:64` 但 video 数组缺 64 档）；durl 模式（platform=html5）
   匿名反而有 720P → **未登录保持 durl 模式，登录态才走 DASH**（登录后 web 端 DASH 上限 1080P）
3. 同一清晰度混发 avc1/hvc1 双编码变体 → **必须按 `codecs.startsWith('avc1')` 过滤**（TV WebView
   H.264 必支持，H.265 不保证）
4. baseUrl 多数落在 PCDN（`*.mcdn.bilivideo.cn:8082`）：**主源 Range 完美**（HTTP 206 + 42ms +
   `acao:*` + ftyp 魔数正确）；两个 backupUrl 对任意 UA 均 403（风控锁死）→ **拉流以主源为通道，
   备源仅在网络错误时轮询兜底**
5. `SegmentBase` 索引完整（`Initialization: 0-914` + `indexRange: 915-2310`）→ 无需顺序扫描
   box，**一次小 Range 拉 init+sidx，解析 sidx 得全部 fragment 的（字节区间, 时间区间）映射**
6. 字段名驼峰/下划线双形态并存（`baseUrl`/`base_url`），取值驼峰优先
7. audio：id 30280(320K)/30232(132K)/30216(64K)，codecs 恒 mp4a.40.2

**fnval=16 而非 4048 的决策**：4048 含 AV1(2048)/HDR(64)/杜比(256+512) 请求位——TV WebView
对 AV1/HEVC 解码不保证，请求了拿到也放不出；16 纯 DASH，B 站下发默认 AVC 编码，最稳。

**MsePlayer 模块（src/player/msePlayer.js）设计**：
- 能力预检：`MediaSource.isTypeSupported('video/mp4; codecs=...')` + `audio` 同
- 流程：new MediaSource → video.src=URL.createObjectURL → sourceopen → 双 SourceBuffer
  （video/audio）→ append init 段（SegmentBase.Initialization）→ 拉 sidx（indexRange）→
  解析出 fragment 索引表 [{startSec, durSec, byteStart, byteEnd}] → 调度循环
- 调度：锚 = currentTime，向前补 AHEAD=20s 窗口；video/audio 独立串行队列
  （appendBuffer 需等 updateend）；append 前滚动清理 buffered 起点早于 currentTime-30s 的段
- seek：remove 全部 buffered → 二分索引表找目标时间的 fragment → 从该处重拉
- duration：init append 后 `mediaSource.duration = dash.duration` 显式设定
- 失败链：网络层自动切备源 → 连续失败/MSE 不支持 → **onFatal 回调 → PlayerView 回退 durl**
- 探针：`window.__mseDebug` 记录 init/sidx/append/error 关键事件（沿用 __dmDebug 套路）
- sidx 解析：reference 表每条 12B（reference_type 1bit + ReferencedSize 31bit +
  SubsegmentDuration 32bit + SAP 相关 32bit），timescale 从 sidx 头部取

**内核层三个实战 bug 与修复**（验证脚本 verify-p8-v1~v5.mjs）：
1. **HAVE_NOTHING 设 currentTime 不派发 seeking**：调用方在 video 无数据时设

2. **resetTo 与 in-flight feed 的 nextIdx 竞态**：feed 的 append 完成回调（nextIdx++）

   晚于 seek 目标 → **seeking 永不完成死锁**（rs 恒 1）。修复：epoch 代际计数，
   append 完成后先查 epoch 再推进 nextIdx
3. **seeking 卡死兜底**：seek 目标处双流数据未齐时浏览器无法完成 seek——feedTick
   检测 seeking 持续 >7s 跳到双流 buffered 交集起点重新定位（实测自愈有效）

### D43 硬件检测与跑分：自动匹配编码/解码器（P9.27，用户需求：检测+跑分匹配最优编解码）

- **入口**：设置页「硬件检测与跑分」行 → 模态面板（设备信息 → 跑分 → 推荐三段渐进渲染）
- **检测（DeviceProbePlugin.getInfo，原生）**：
  - 设备：厂商/型号/Android 版本/API 级/SoC（API31+ 用 Build.SOC_MODEL，低版本 HARDWARE）/
    核数/内存 GB/GLES 版本/模拟器标记（与 D42 同套启发式）
  - 硬解支持：MediaCodecList 枚举非 encoder 且 isHardwareAccelerated（API<29 按名称启发式
    OMX.google/c2.android=软解），标记 video/avc、video/hevc、video/av01
- **跑分（benchCpu，原生）**：min(核数,8) 线程 × 1.2s 定时长循环，xorshift 整数 + 周期 sqrt
  （防 JIT 死码消除），返回 Mops/s；Web 环境回退单线程 JS 基准 × 核数近似
- **档位**：≥400 强 / 120~400 中 / <120 弱（Mops/s，覆盖主流电视~旗舰量级）
- **推荐匹配（analyzeDevice，硬解支持优先）**：
  1. 模拟器 → sw + default（GPU 转译绿屏，D42）
  2. 硬解 AV1 → hw + av01（同画质带宽最优）
  3. 硬解 HEVC → hw + hev1（硬解不占 CPU，弱机也推荐）
  4. 仅硬解 AVC → hw + default（avc1 优先兼容性最好）
  5. 无硬解 + CPU 中/强 → sw + default
  6. 无硬解 + CPU 弱 → hw + default（selector 空集自动回退系统默认解码器）
- **应用推荐**：写 settings.decoder + settings.defaultCodec，同时标记 decoderTouched（尊重
  用户显式选择，模拟器自动软解策略不再覆盖）；面板同时展示当前值对比与分辨率建议文案

  - 450ms 内 keyup = 短按结束（共 1 次步进）；450ms 无 keyup = 进入**连进模式**：每 220ms
    seek 一次，步长 30s 起每次 +30s、封顶 120s（bbll 式越按越快）
  - keyup 任何时候结束连进；`e.repeat === true` 的 keydown 全部忽略（连进步进由自有
    定时器驱动，不依赖系统重复频率——遥控器/键盘 repeat 速率不可控）
- **focus.js 拦截器签名升级**：`fn(key)` → `fn(key, e)`（第二参传原始 KeyboardEvent，
  向后兼容；连进需要 e.repeat 与 keyup——keyup 由 PlayerView 自行 window 监听，引擎不拦 keyup）
- **按键语义（OSD 隐藏态，bbll 对齐）**：
  - ←/→：短按 ±10s / 长按连进（原 ±10s 单击扩展）
  - ↑：呼出播放控制栏（原有保留）
  - ↓：打开选集列表（原「聚焦推荐卡」保留于焦点在推荐列时——列内导航优先）
  - OK：播放/暂停（原有保留）
- **Seek HUD 反馈**：视频区中下胶囊浮层，连进时显示方向箭头（«/»）+ 步长 + 目标时间
  （如「»» 60s → 02:31」），1.2s 无操作淡出；长按全程持续刷新
- **OSD 显示态不变**：方向键走引擎焦点导航、Esc 关栏——长按连进仅隐藏态生效，互不冲突

### D35 关注动态流（P9.12，对齐 web t.bilibili.com/?tab=video）

- **旧方案瓶颈**：「全部」聚合流 = 前 10 UP × searchAll 串行批（约 5-6 秒）且非真实时间序

    携带 bvid/title/pic/duration_text/stat，module_author 携带 name/pub_ts
- **收益**：1 个请求替代 10 个 searchAll（<1 秒）；真实时间序；覆盖全部关注 UP（不限前 10）；
  触底 offset 懒加载

  缓存键 followAll（cursor 存 offset）/ follow-<mid>；触底 loadMoreDyn
